# Encrypted Transport — ETR v1.0

## 1. PURPOSE AND SCOPE

ETR v1.0 is the deterministic symmetric authenticated-encryption runtime that seals ACP payloads and artifact files into ChaCha20-Poly1305 AEAD envelopes and opens them back with authentication verification. ETR consumes CKS keys read-only, persists transport channels and envelope records under PESE `transport_state` with transition type `TRANSPORT_STATUS`, and emits `ETR_*` events to the EEF execution journal.

Today an operator has no machine-verifiable way to seal an ACP payload or artifact file, transport it, and prove on the receiving end that it has not been tampered with. ETR closes that gap with a pure-Python, stdlib-only implementation of RFC 8439 ChaCha20-Poly1305 AEAD, deterministically keyed by 32-byte CKS symmetric keys.

**Boundary.** ETR manages transport channels and sealed envelopes using CKS keys, PESE state, and EEF events. It does not generate or rotate keys (CKS owns those), define agent lifecycle transitions (AGC), schedule dispatch (EEF/AEX), manage risks (RKM), validate gates (VAL), assemble teams (TBE), assemble missions (MSS), diagnose health (AHP), orchestrate recovery (REC), validate state (VAL), or execute work (AEX).

## 2. ARCHITECTURE AND BOUNDARY

ETR operates as a deterministic encryption runtime layered on the existing runtimes:

```text
+-----------------------------------------------+
|     Operators / CLI / ACP / AEX / agents      |
+-----------------------------------------------+
| ETR v1.0  (this contract)                     |
|   - ChaCha20-Poly1305 AEAD seal / open        |
|   - channels (ACTIVE/REVOKED)                  |
|   - envelopes (SEALED/OPENED/AUTH_FAILED)      |
|   - ETR_* events to EEF journal                |
+-----------------------------------------------+
| CKS v1.0  (read-only: symmetric key lookup)    |
| PESE v1.0 (read/write: transport_state)        |
| EEF v1.0  (append: execution events)           |
+-----------------------------------------------+
```

**Key design decisions:**

1. All channel and envelope mutations flow through `PESEStore.update()` with transition type `TRANSPORT_STATUS`. ETR never writes PESE state directly; it relies on the store's legal-transition enforcement and actor authorization.
2. ETR enforces its own channel and envelope state machines because `TRANSPORT_STATUS` is not in PESE's legal-transition map (same pattern as AGC's `AGENT_STATUS`, RKM's `RISK_STATUS`, VAL's `VALIDATION_GATE`, and REC's `RECOVERY_STATUS`).
3. Transport state lives under the PESE top-level key `transport_state`, containing `channels` (keyed by channel_id) and `envelopes` (keyed by envelope_id). PESE's `default_state()` includes it and `_validate_state_shape()` permits it as optional; the key is present in fresh `default_state()` and optional in validation so pre-ETR states continue to validate.
4. The AEAD nonce is the single non-deterministic input, generated by `secrets.token_bytes(12)`, matching the standard CKS key-generation pattern. All other envelope fields are deterministic.
5. The envelope's AAD (associated authenticated data) is derived from the canonical JSON of the header fields (format, cipher, key_id, nonce, metadata). Any tampering with header fields invalidates the authentication tag at open time, and the entire record transitions SEALED → AUTH_FAILED.
6. Channel-based seal automatically resolves `from_id`, `to_id`, and `key_id` from the channel record, eliminating manual key management in ACP session flows.
7. Lock discipline: ETR holds a per-path reentrant lock for the duration of each operation, keyed by the PESE directory path.

## 3. CHANNEL AND ENVELOPE SCHEMA

### Transport Channel

Each channel is stored in `transport_state.channels[channel_id]`:

```json
{
  "channel_id": "CHANNEL:7f3a...",
  "format": "ETR/v1.0",
  "from": "AGENT:sender:local",
  "to": "AGENT:receiver:local",
  "key_id": "KEY:abc123",
  "status": "ACTIVE",
  "created_at": "2026-08-06T04:00:00.000Z",
  "updated_at": "2026-08-06T04:00:00.000Z",
  "revoked_at": null
}
```

| Field | Meaning |
|---|---|
| `channel_id` | Canonical channel identifier, unique across all channels (`CHANNEL:<uuid4>`) |
| `format` | ETR format marker, always `ETR/v1.0` |
| `from` | Sender identity (agent or session id) |
| `to` | Recipient identity (agent or session id) |
| `key_id` | The CKS key this channel is bound to |
| `status` | Current channel status (ACTIVE or REVOKED) |
| `created_at` | UTC timestamp when the channel was bound |
| `updated_at` | UTC timestamp of the last update |
| `revoked_at` | UTC timestamp when revoked, or null |

**Channel status vocabulary:**

| Status | Meaning |
|---|---|
| `ACTIVE` | Channel is bound to a valid CKS key and may be used for sealing |
| `REVOKED` | Channel has been permanently revoked; no new seals allowed |

**Legal transitions (ETR-enforced):**

| From | To |
|---|---|
| `ACTIVE` | `REVOKED` |

There are no reverse transitions.

### Sealed Envelope

Each envelope is stored in `transport_state.envelopes[envelope_id]`:

```json
{
  "envelope_id": "ENVELOPE:a1b2...",
  "format": "ETR/v1.0",
  "cipher": "CHACHA20-POLY1305",
  "key_id": "KEY:abc123",
  "nonce": "010203...",
  "aad": "7b22666f...",
  "ciphertext": "d31a8d34...",
  "tag": "1ae10b59...",
  "plaintext_sha256": "e3b0c442...",
  "message_type": "ACP",
  "from": "AGENT:sender:local",
  "to": "AGENT:receiver:local",
  "mission_id": "MISSION:example",
  "correlation_id": null,
  "status": "SEALED",
  "created_at": "2026-08-06T04:00:00.000Z",
  "opened_at": null
}
```

| Field | Meaning |
|---|---|
| `envelope_id` | Canonical envelope identifier (`ENVELOPE:<uuid4>`) |
| `format` | ETR format marker, always `ETR/v1.0` |
| `cipher` | Cipher identifier, always `CHACHA20-POLY1305` |
| `key_id` | The CKS key used for encryption |
| `nonce` | 12-byte nonce, hex-encoded (the non-deterministic input) |
| `aad` | Canonical JSON of the header fields, hex-encoded (bound to ciphertext) |
| `ciphertext` | ChaCha20-encrypted payload, hex-encoded |
| `tag` | Poly1305 authentication tag, hex-encoded (16 bytes) |
| `plaintext_sha256` | SHA-256 digest of the original plaintext |
| `message_type` | Optional ACP message type (e.g. `ACP`, `STATUS`, `ASSIGNMENT`) |
| `from` | Sender identity, resolved from channel if channel-based |
| `to` | Recipient identity, resolved from channel if channel-based |
| `mission_id` | Optional owning mission identifier |
| `correlation_id` | Optional correlation identifier |
| `status` | Current envelope status (see below) |
| `created_at` | UTC timestamp when the envelope was sealed |
| `opened_at` | UTC timestamp when opened, or null |

**Envelope status vocabulary:**

| Status | Meaning |
|---|---|
| `SEALED` | Envelope is sealed and has not been opened |
| `OPENED` | Envelope was successfully authenticated and opened |
| `AUTH_FAILED` | An open attempt failed Poly1305 tag verification (tamper detected) |

**Legal transitions (ETR-enforced):**

| From | To |
|---|---|
| `SEALED` | `OPENED`, `AUTH_FAILED` |

There are no reverse transitions.

## 4. AEAD ENVELOPE FORMAT

ETR uses RFC 8439 ChaCha20-Poly1305 AEAD:

- **Key**: 32-byte CKS symmetric key (HMAC-SHA256 derivation)
- **Nonce**: 12 bytes, generated by `secrets.token_bytes(12)` (unique per envelope)
- **AAD**: Canonical JSON of `{"format", "cipher", "key_id", "nonce", "message_type", "from", "to", "mission_id", "correlation_id"}`, hex-encoded — binding all metadata to the ciphertext
- **Plaintext**: Raw file bytes (non-empty)
- **Ciphertext**: ChaCha20 stream XOR plaintext
- **Tag**: 16-byte Poly1305 MAC over `AAD || ciphertext || pad16(AAD) || pad16(ciphertext)`

Any modification to the AAD fields, ciphertext, or tag fails the authentication check at open time, and the envelope transitions to `AUTH_FAILED`.

The Poly1305 key derivation follows RFC 8439 §2.6: the first 32 bytes of the ChaCha20 keystream with counter=0 (encrypting an all-zero block) produce the r/s key, clamped as specified.

## 5. LIFECYCLE

### Channel Lifecycle

```text
bind_channel ──► ACTIVE ──► REVOKED
```

1. `bind_channel(from_id, to_id, key_id, actor)` — validates key exists and is ACTIVE, creates an ACTIVE channel, persists via PESE, emits `ETR_CHANNEL_BOUND`.
2. `revoke_channel(channel_id, actor)` — transitions ACTIVE → REVOKED, persists, emits `ETR_CHANNEL_REVOKED`.

### Envelope Lifecycle

```text
seal ──► SEALED ──► OPENED
               └──► AUTH_FAILED
```

1. `seal(payload, key_id=..., actor=...)` — encrypts the payload, writes to PESE, emits `ETR_SEALED`.
2. `open(envelope, actor=...)` — recomputes AAD from current header, verifies Poly1305 tag:
   - On success: transitions SEALED → OPENED, emits `ETR_UNSEALED`, returns `UnsealedPayload`.
   - On failure: transitions SEALED → AUTH_FAILED, emits `ETR_AUTH_FAILED`, raises `EtrError("AUTH_FAILED", ...)`.

## 6. EVENT JOURNAL

Every channel and envelope mutation emits an event to the EEF execution journal (hash-chained `execution-events.jsonl`). Events use the `ETR_*` event types registered in the EEF `EVENT_TYPES` frozenset:

| Transition | Event Type |
|---|---|
| Channel bound (ACTIVE created) | `ETR_CHANNEL_BOUND` |
| Channel revoked (ACTIVE → REVOKED) | `ETR_CHANNEL_REVOKED` |
| Envelope sealed (SEALED created) | `ETR_SEALED` |
| Envelope opened (SEALED → OPENED) | `ETR_UNSEALED` |
| Envelope auth failed (SEALED → AUTH_FAILED) | `ETR_AUTH_FAILED` |

Event emission is best-effort: exceptions are swallowed so journal failures never block channel or envelope mutations. The journal event includes `key_id`, `from`/`to` (channel), or `key_id`, `message_type`, `plaintext_sha256` (seal) / `key_id` (open/auth-fail) in the `detail` field.

## 7. CLI REFERENCE

All commands accept `--root <path>` (default: current directory) and emit machine-readable `key=value` output to stdout. Deterministic exit codes: 0 for success, 2 for error/failure.

| Command | Description | Exit 2 on |
|---|---|---|
| `etr-bind-channel` | Bind an ACTIVE transport channel to a CKS key | key not found, bad channel args |
| `etr-revoke-channel` | Revoke an ACTIVE transport channel | channel not found, channel not active |
| `etr-channel` | Read a single transport channel snapshot | channel not found |
| `etr-list-channels` | List transport channels (optionally filtered) | — |
| `etr-seal` | Seal a payload file into a ChaCha20-Poly1305 envelope | file missing, key/channel required, empty payload |
| `etr-open` | Authenticate and open an envelope (by id or envelope file) | envelope not found, bad envelope, auth failed |
| `etr-list-envelopes` | List sealed envelopes (optionally filtered) | — |
| `etr-report` | Aggregated transport summary | — |

**Arguments:**

- `etr-bind-channel`: `--from` (required), `--to` (required), `--key-id` (required), `--actor` (optional).
- `etr-revoke-channel`: `--channel-id` (required), `--actor` (optional).
- `etr-channel`: `--channel-id` (required), `--actor` (optional).
- `etr-list-channels`: `--from` (optional filter), `--to` (optional filter), `--status` (optional filter), `--actor` (optional).
- `etr-seal`: `--file` (required), `--key-id` (optional), `--channel-id` (optional), `--message-type` (optional), `--from` (optional), `--to` (optional), `--mission-id` (optional), `--correlation-id` (optional), `--output` (optional), `--actor` (optional). Exactly one of `--key-id` or `--channel-id` is required.
- `etr-open`: `--envelope` (required: envelope id or path to `.etr` JSON file), `--output` (optional: write plaintext to this path), `--actor` (optional).
- `etr-list-envelopes`: `--key-id` (optional filter), `--message-type` (optional filter), `--status` (optional filter), `--actor` (optional).
- `etr-report`: `--actor` (optional).

**Output examples:**

`etr-bind-channel`:


## 8. ERROR HANDLING

| Error Code | When |
|---|---|
| `BAD_CHANNEL` | `from_id` or `to_id` is empty in `bind_channel` |
| `PERSIST_FAILED` | PESE update returned a non-UPDATED outcome |
| `CHANNEL_NOT_FOUND` | Requested `channel_id` does not exist in `transport_state.channels` |
| `CHANNEL_NOT_ACTIVE` | Attempted operation on a non-ACTIVE channel (e.g. revoke a REVOKED channel, seal via a REVOKED channel) |
| `ENVELOPE_NOT_FOUND` | Requested `envelope_id` does not exist in `transport_state.envelopes` |
| `ENVELOPE_NOT_OPENABLE` | Attempted to open a non-SEALED envelope (already OPENED or AUTH_FAILED) |
| `EMPTY_PAYLOAD` | `seal()` received an empty payload |
| `KEY_REQUIRED` | Neither `key_id` nor `channel_id` was supplied to `seal()` |
| `BAD_ENVELOPE` | Envelope record is malformed, missing fields, or has unsupported format |
| `AUTH_FAILED` | Poly1305 tag verification failed; envelope transitions to AUTH_FAILED |

## 9. ON-DISK LAYOUT

ETR state is persisted within PESE's canonical layout:

```text
.project-os/
├── PESE/
│   ├── live.json          ← transport_state.channels, transport_state.envelopes
│   └── ...
└── AUDIT/
    └── execution-events.jsonl   ← ETR_* events appended here
```

Channel and envelope records live in `state.transport_state.channels[channel_id]` and `state.transport_state.envelopes[envelope_id]` respectively. These keys are created lazily by `state.setdefault("transport_state", {"channels": {}, "envelopes": {}})` and are present in fresh `default_state()`.

Envelope files (when using `seal_file`) are written to the caller-specified output path or `{source}.etr` by default. Envelope files are standard JSON records identical to the PESE envelope record.

## 10. COMPATIBILITY

ETR v1.0 is additive — it adds transport channels and sealed envelopes to existing PESE state without modifying any prior contract. Existing PESE, TBE, MSS, EEF, CKS, AEX, AHP, VAL, RKM, AGC, and REC commands continue to work unchanged.

The `TRANSPORT_STATUS` transition type is not in PESE's legal-transition map; ETR enforces its own channel and envelope state machines (same pattern as AGC's `AGENT_STATUS`, RKM's `RISK_STATUS`, VAL's `VALIDATION_GATE`, and REC's `RECOVERY_STATUS`). The `transport_state` key is optional in PESE's state-shape validation so states initialized before ETR v1.0 remain valid.

The `seal()` method accepts exactly one of `key_id` or `channel_id`; channel-based seal resolves `from_id`, `to_id`, and `key_id` from the channel record automatically. The `open()` method accepts an envelope id (PESE lookup) or a mapping (e.g. loaded from an `.etr` JSON file), enabling both state-tracked and standalone file-based workflows.

## 11. IMPLEMENTATION REQUIREMENTS

1. `src/asc_orchestrator/etr.py` must implement `EncryptedTransport`, `EtrError`, `TransportChannel`, `SealedEnvelope`, `UnsealedPayload`, and `TransportReport` using only stdlib.
2. ChaCha20-Poly1305 AEAD must follow RFC 8439 exactly, including Poly1305 r-clamping, pad16, and key derivation (§2.6).
3. All channel and envelope mutations must flow through `PESEStore.update()` with `transition_type="TRANSPORT_STATUS"`.
4. Channel-based seal must resolve `key_id`, `from_id`, and `to_id` from the channel record when `channel_id` is supplied.
5. AAD must be derived from the canonical JSON of the header fields (format, cipher, key_id, nonce, message_type, from, to, mission_id, correlation_id) so any metadata tampering fails authentication.
6. Event emission must use `EEFEventJournal.append()` with the five `ETR_*` event types.
7. PESE must register the `transport_state` top-level key in `default_state()` and permit it in `_validate_state_shape()` (optional).
8. Eight `etr-*` CLI subcommands must emit machine-readable `key=value` output and deterministic exit codes.
